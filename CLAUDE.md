# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Personal Attendance Discipline System — a native Android check-in/check-out tracker that enforces daily work discipline. Tracks net daily hours via auth-gated check-in/out intervals, calculates a rolling leave deficit, and presents compliance status. Modeled after an office fingerprint attendance system. The app is branded **CheckIn**.

**Attendance rules:**
- Net time = sum of all completed check-in/out intervals per day, each interval minus any paused (unverified-presence) time (open intervals between check-ins are excluded)
- Every day counts (7 days/week — no weekends/holidays exemption)
- Leave deduction is relative to the day's **target** (the "present mark"): `≥ target` = present (0.0), `≥ target/2` = half-day (0.5), `< target/2` = full-day leave (1.0)
- Deficit accumulates forever from the tracking start date — there is no leave quota, the deficit only grows. It is computed but **rendered nowhere**; see the gotcha below before treating `DeficitCalculator` as dead code
- **Sessions are immutable** — no edit/delete/manual entry by design
- Every check-in AND check-out is gated by a presence check: an on-device ML Kit face detection (offline), with **device biometric** as a fallback after repeated face failures
- Self-contained: Room-only persistence, no backend; CSV export via share sheet

## Build Commands

The Gradle wrapper is checked in and pinned to **Gradle 8.13** (the project's Kotlin 1.9.20 + AGP 8.13.2 are incompatible with Gradle 9.x, which removed `HasConvention`).

`gradle/gradle-daemon-jvm.properties` requires a **JetBrains vendor JDK 21** for the daemon — the one bundled with Android Studio (`/Applications/Android Studio.app/Contents/jbr/Contents/Home`). Android Studio finds it automatically. For **CLI builds**, point Gradle's toolchain detection at it:

```bash
export JBR="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:testDebugUnitTest -Dorg.gradle.java.installations.paths="$JBR"  # JVM unit tests
./gradlew :app:assembleDebug     -Dorg.gradle.java.installations.paths="$JBR"  # Build debug APK
./gradlew :app:installDebug      -Dorg.gradle.java.installations.paths="$JBR"  # Install on a device
./gradlew staticAnalysis         -Dorg.gradle.java.installations.paths="$JBR"  # ktlint + detekt
./gradlew :app:verifyLicenseCoverage -Dorg.gradle.java.installations.paths="$JBR"  # licence list vs classpath
./gradlew ktlintFormat           -Dorg.gradle.java.installations.paths="$JBR"  # Auto-fix formatting
```

Run a single test class: `./gradlew :app:testDebugUnitTest --tests "com.checkin.app.DeficitCalculatorTest"`.

**Static analysis** is **ktlint** (via `org.jlleitschuh.gradle.ktlint`, engine pinned to 1.5.0) and
**detekt** 1.23.8, applied to every project including the root build script. `staticAnalysis` is the
one task CI and the pre-commit hook both call. Formatting rules come from `.editorconfig`
(`intellij_idea` style, matching `kotlin.code.style=official`; 120 columns; `@Composable` exempted
from ktlint's camelCase `function-naming` rule). Detekt's overrides are `config/detekt/detekt.yml`
with `buildUponDefaultConfig = true`, so the file only states what differs, and nothing there
duplicates a ktlint check (`MaxLineLength` is off for exactly that reason). **There is deliberately
no detekt baseline file** — `baseline.xml` is wired up in the root build script but does not exist,
because the tree is clean. Adding one would convert a finding into permanent, invisible debt; the
intended responses to a new finding are a real fix or a site-level `@Suppress` carrying the reason
(see `CheckInService.logPresenceEvent`, `DefaultCsvExporter.export`, `SelfieCaptureScreen`).

A **pre-commit hook** (`githooks/pre-commit`, enabled per clone with `git config core.hooksPath
githooks`) runs the same `staticAnalysis` task. It exits early when no `.kt`/`.kts` file is staged,
and refuses outright to commit a `*.jks` / `keystore.properties` / `local.properties` — `git add -f`
can otherwise defeat `.gitignore`, and a leaked upload key is unrecoverable. Tests are deliberately
not in the hook; they are CI's job.

Toolchain: **JDK 17** source/target compatibility. Android **SDK 36** (`compile`/`target`, Android 16 — Play's target-API floor from 2026-08-31), **min SDK 34** (Android 14). Unit tests live in `app/src/test/java/com/checkin/app/` and are pure JVM (no Robolectric).

**Versioning** is centralized in `gradle.properties` (`VERSION_CODE` / `VERSION_NAME`), read by `app/build.gradle.kts` (with `-P` override support). **`VERSION_CODE`** is the integer Play orders builds by — scheme is **`YYYYMMDD` of the release day, set manually** (must be strictly higher than any code already uploaded, app-wide; users never see it). One uploadable build per day; for a rare same-day rebuild, `+1` or append a 2-digit counter (`YYYYMMDDNN`). **`VERSION_NAME`** is the user-facing SemVer `MAJOR.MINOR.PATCH` label — bump when meaningful. Promoting the *same* `.aab` across tracks (internal → production) reuses its code; only a rebuild needs a new one.

**CI** (`.github/workflows/ci.yml`) runs `staticAnalysis` first — it needs no compiled classpath, so a style or smell failure reports in seconds instead of after a full assemble — then `:app:testDebugUnitTest` + `:app:verifyLicenseCoverage` + `:app:assembleDebug` on push/PR to `main`. It provisions a JetBrains Runtime 21 via `actions/setup-java` (`distribution: jetbrains`) to satisfy the daemon-JVM criteria, then passes `-Dorg.gradle.java.installations.paths="$JAVA_HOME"` — the CI mirror of the local `$JBR` flag above. The Android SDK is the one preinstalled on the runner.

## Architecture

**MVVM with Jetpack Compose + Room + Foreground Service + CameraX + ML Kit + BiometricPrompt.** Manual DI (no framework): `CheckInApplication` holds an `AppContainer` (`di/`) that builds the `CheckInRepository`, the side-effect seams (`AttendanceSettings`, `ServiceController`, `CsvExporter`), the `TimeSource`, and an app-wide `CoroutineScope`. Each `ViewModel` is constructor-injected via a `viewModelFactory`, exposes **one** reactive `UiState` (`StateFlow` built with `stateIn`/`flatMapLatest` over Room `Flow`s), and is JVM-unit-tested with fakes.

```
UI (4-Tab Compose Screens) → ViewModel (one UiState StateFlow) → Repository → Room DAO → SQLite
                                    ↕
                           CheckInService (foreground service; timer + presence-check reminder)
                                    ↕
                           Presence gate: CameraX + ML Kit face detection → BiometricPrompt fallback
```

- **Pure/testable core** (no Android deps, unit-tested):
  - `data/local/AttendanceRules` — single source of truth for status classification and leave fractions
  - `data/local/TargetSchedule` — the immutable per-day target log (see gotchas)
  - `data/DeficitCalculator`, `data/AttendanceStats` — deficit and streak/summary math
  - `data/TimeSource` (`SystemTimeSource`) — injectable clock so date logic is deterministic in tests
  - `service/ReminderScheduler` — reminder timing; `service/PresenceCheckPolicy` — retry maths; `service/SessionClock` — the ongoing notification's elapsed time and chronometer origin; `ui/camera/AuthGate` — biometric-fallback decisions
  - `util/TimeFormat` — the one place durations, clock times **and dates** are formatted
- **Room** — single entity `CheckInSession` (table `sessions`): `id`, `started_at`, `stopped_at` (null while active), `duration` (null until check-out; net of paused time), `date_key` (`yyyy-MM-dd`, the check-in day), `paused_ms` + `pause_started_at` (presence-pause accounting — see gotchas). DB name `"_app"`, version 4 (v2→v3 `MIGRATION_2_3` adds the two pause columns; v3→v4 `MIGRATION_3_4` drops the former vestigial `punch_in_selfie`/`punch_out_selfie` columns — both migrations preserve data; `fallbackToDestructiveMigration()` remains the backstop).
- **CheckInService** — `specialUse` foreground service showing the ongoing timer notification, and **only** that. It no longer runs a ticker and no longer owns the presence check: the notification's elapsed time is drawn by the platform chronometer from one post, and the check runs off an alarm (`PresenceCheckRunner`). It posts on state changes — start, pause, resume, teardown — a handful of times per session. Persists a render mirror in `checkin_timer_prefs` to survive process death (`START_STICKY`). The **DB row is authoritative**: those prefs are advisory cache, read only so the notification posted inside the foreground-start deadline isn't blank, and every command reconciles against the active session via `ServiceReconciler` — a closed/absent row tears the service down (no orphan notification), a live row's pause state is adopted (no phantom pause), and an in-flight reconcile is cancelled first so a stale snapshot can't clobber fresher state. `CheckInService.isRunning` is what `SessionWatchdog` reads to tell a live service from a killed one.
- **Presence gate** — `PresenceGate` is the single entry point and the only place either runtime permission is asked for: it renders the prominent disclosure, then the `CAMERA` + `POST_NOTIFICATIONS` request, then `SelfieCaptureScreen`, and both call sites (the root gate in `MainActivity`, the in-app gate in `AppNavScaffold`) go through it. `SelfieCaptureScreen` captures a front-camera frame; `FaceDetectionHelper` (ML Kit) must find a face. The image is **deleted as soon as the outcome is known** (detection + deletion run on the app-wide `AppContainer.applicationScope`, not the composition, so a mid-capture dismiss can't strand the file); the camera bind is guarded so a dismiss before the provider resolves still releases it. `AuthGate.BIOMETRIC_FALLBACK_AFTER` (3) consecutive failures — of any kind, no-face **or** capture error — offer a device-unlock (`BiometricPrompt`) fallback. `MainActivity` is a `FragmentActivity` (required by `BiometricPrompt`). The root gate is driven by `PresenceCheckSignal.request` (a `Reason`: `REAUTH` from the reminder tap, or `CHECK_OUT` from the ongoing notification's action). The gate and the nav host render **mutually exclusively** (gate XOR host), but `rememberNavController()` is **hoisted above the switch** so the gate preserves the active tab and back stack; a `BackHandler` dismisses the gate, and the triggering intent extra is consumed once so recreation doesn't replay it. On success, `REAUTH` re-arms the reminder (resuming a paused clock) and `CHECK_OUT` checks the active session out.

## Gotchas & Non-Obvious Behaviors

- **The daily target is per-day and immutable.** Changing the target slider records `(today, hours)` in the `TargetSchedule` log (`attendance_prefs` key `target_schedule`); each day is classified against the target in effect **on that date**, so past days keep their original classification. Thresholds derive from that target (present `= target`, half `= target/2`). The log is seeded at the first check-in. For installs that predate the log (they have `tracking_start_date` + the legacy scalar `daily_target_hours` but no `target_schedule`), `AttendancePrefs.readSchedule` synthesizes a single entry `(tracking_start, daily_target_hours)` so the old target isn't silently lost to the default — do all schedule reads through that helper.
- **Nothing is asked for at launch — the app opens straight into the nav host.** The disclosure and both runtime permissions were once a blocking startup sequence; they now live inside `PresenceGate` and are raised only when a check actually needs them, which in practice is the first check-in. Attendance, Reports and Settings are therefore fully browsable by a user who has never granted anything, and a *revoked* camera permission no longer locks the whole app out — it surfaces at the next check. Consequences worth knowing before moving any of it back: the gate must ask on entering the "disclosed but ungranted" state rather than only on the disclosure's Continue button, or a permission revoked between sessions strands the user on a recovery screen that never prompts; a `LifecycleResumeEffect` re-reads the grant because the recovery screen's escape hatch is system settings, which returns with no result; and `CameraDisclosureScreen` now carries a **Not now** button, since a screen that interrupts a check-in needs an exit that isn't the back gesture. Only the camera decides whether a check can run — a refused `POST_NOTIFICATIONS` costs the timer notification and the reminder, both already guarded by `Notifier`.
- **Selfies are transient.** The captured JPEG is deleted immediately after face detection resolves (success or failure) — nothing accumulates in `filesDir/selfies/`, and no image is ever displayed. `SelfieStorage` owns the directory and its `sweep()` runs once at startup (from `AppContainer`) to clear any file orphaned by process death between the frame write and that delete.
- **Three SharedPreferences namespaces.** `attendance_prefs` (settings + `target_schedule` + `tracking_start_date` + the two presence-check flags, keys **and readers** — `readSchedule`/`readTrackingStart` — centralized in `data/AttendancePrefs`, used by all four ViewModels and `CheckInService`); `checkin_timer_prefs` (live timer + reminder + pause state in `CheckInService`); `engagement_prefs` (nudge opt-ins, per-nudge send history, install id — behind the `EngagementSettings` seam). Keeping the third separate is what lets engagement state be wiped without touching the tracking start or the target schedule. **`presence_check_enabled`/`presence_check_pauses` live in the first namespace even though the Settings screen renders them beside the nudge toggles** — they decide how worked time is *counted*, so `clearHistory()` on engagement state must not be able to alter someone's hours.
- **Two databases.** `_app` (v4) holds attendance. `engagement.db` (v2 — `MIGRATION_1_2` adds the `source` column) holds only notification analytics and is deliberately a *separate* Room database — an experiment redesign can drop and recreate it with `fallbackToDestructiveMigration` without ever putting a user's attendance records at migration risk, and no schema change there widens the CSV export. The cost is that conversion attribution can't be a SQL join, so it happens in Kotlin via `AttributionRules`. **Presence-check reminders are logged here too, and the `source` column is what keeps them harmless.** `countOfTypeSince` (the nudge daily cap) and `latestOfType` (tap and conversion attribution) are both scoped to `source = 'NUDGE'`; unscoped, a presence check would consume the day's single nudge slot or take credit for a check-in it never caused. Service-lifecycle rows use a third source, `SERVICE`, and are scoped out of the same two queries for the same reason. `recent()` is deliberately unscoped so the diagnostics card shows everything. `FakeEngagementLog` mirrors the same scoping — otherwise a test could only ever prove the fake right — and `EngagementLogSourceTest` pins all of it. The names are now a half-truth (`EngagementLog`, `engagement.db`, `engagement_events`, `engagement_prefs` all hold presence rows too) and are kept anyway: a rename means either a new DB file, which orphans the send history the daily cap counts from, or a migration for a column name nothing reads.
- **The nav scaffold owns the screen title.** `AppNavScaffold` renders a `CenterAlignedTopAppBar` whose title is the active `Screen.titleRes`, driven by the same back-stack subscription as the bottom nav — screens never draw their own heading, and they receive the combined top inset through the Scaffold's `innerPadding`. `Screen` splits into `Tab` (a bottom-nav destination) and `Detail` (pushed above a `parent` tab: back arrow instead of a centred-only title, and the parent stays lit below so a sub-screen still reads as part of its section). **A new destination must be added to `titledScreens` (in `ui/navigation/Screen.kt`, alongside the hierarchy itself), not just to the nav graph in `BottomNavigation.kt`** — the title lookup falls back to `Screen.CheckIn`, so a route missing from that list renders a screen labelled "Check In" rather than failing. **A tab tap pops any open `Detail` before it navigates**, because the bar's `popUpTo(start) { saveState = true }` + `restoreState = true` would otherwise save the detail *into* its parent tab's back stack — tapping the lit Settings tab from Licenses would then restore Licenses, and the tab would read as dead. `SettingsViewModel` is the one VM that is prefs-only (no Room `Flow`), so it re-reads on resume and after each write rather than building a reactive pipeline.
- **Tracking starts at the first authenticated check-in**, not first launch — `CheckInViewModel` seeds `tracking_start_date` there via `AttendanceSettings.seedTrackingStartIfNeeded()`. There is no UI to change it (by design).
- **Stats exclude today** — computed from the tracking start up to yesterday. Today's in-progress day never counts. The Attendance month summary (present/half/absent counts **and** both averages alike) and the calendar cell for today follow the same rule: today is shown unclassified (its "today" marker only), not counted as leave until it becomes a completed past day. The "today" boundary comes from an injectable day clock (`TimeSource.currentDay()`), so at midnight the screens roll over **live** — the averaging window, tracked-day counts, and the "today" marker advance without waiting for a screen resume. Only the Attendance *displayed month* stays put until the user navigates.
- **The engagement layer is structurally isolated, and that is the point.** `notify/` may *read* attendance state to build an `EngagementSnapshot`, but it never writes to `sessions`. The entire decision surface is `NudgeEligibility.select(snapshot)` — a pure function of a plain value object, no clock, no DB, no Android — so experiments in timing, capping and targeting are changes to one unit-tested function. **There is no app-level quiet-hours window and adding one back would be a mistake**: Android's per-channel settings already give the user that control, and the app's own version only ever applied to nudges while the presence check and the timer notification ignored it — a promise ("Nothing is sent between…") the app did not keep. Frequency is bounded by the daily cap and the per-nudge cooldown instead. Two places deliberately touch app code: `PresenceCheckSignal.Reason.CHECK_IN` (nudge tap → gate) and the `EngagementReporter` seam. That seam's `onCheckedIn` is called from **both** check-in writers — `CheckInViewModel.executeCheckIn` and `MainActivity.onRootGatePassed` — because a nudge the user acted on from inside the app converted just as much as one they tapped; wiring it only to the tap path would report 0% for a nudge that worked. It also cancels the now-stale nudge notification, since nothing the app posts is `autoCancel`. **Nudges are opt-in and default OFF** — both the master switch and each individual nudge — so shipping the foundation messages nobody until asked. The isolation is enforced at runtime too: `CheckInService` writes presence rows through `logPresenceEvent`, which swallows a failed write, because `serviceScope` has no exception handler and a full or corrupt `engagement.db` would otherwise take the foreground service — and with it the user's running timer — down with it.
- **A nudge tap is still gated.** `EXTRA_CHECK_IN` opens the root presence gate exactly like the reminder and check-out paths; success then checks in. Check-in is never un-gated, and the handler re-checks for an active session first, since the user may have checked in between the notification being posted and tapped. `repository.checkIn()` is the backstop for that check: it returns the open session rather than inserting a second, because two rows with `stopped_at IS NULL` would leave one open forever. A presence request is never queued and never outlives its tap. `PresenceGate` owns the disclosure and both permissions, so the gate always opens on the spot — there is no screen a reason could sit behind. What it can still do is go unanswered: the gate parks indefinitely on the disclosure, the camera-recovery screen or the capture, and pressing Home leaves the reason set on a process-global flow nothing else clears. So `PresenceCheckSignal.raise` stamps the request and `MainActivity.onStart` calls `expireIfStale`, dropping anything older than `EXPIRY_MS` (10 minutes) before it can reopen. **The check is on start, not on stop**, because leaving the app is exactly what the gate's legitimate path does — the recovery screen sends the user to system settings and expects them back — and only elapsed time separates that round trip from abandonment. Without it a nudge tapped at 09:00 and abandoned reopens that evening and, on success, writes a check-in stamped at whatever day it had become, onto a row the app deliberately gives no way to edit. `PresenceCheckSignalTest` pins the boundary and the round trip.
- **Nudge timing is best-effort by design.** `NudgeWorker` is an hourly `PeriodicWorkRequest` (`KEEP`, so it survives reboots and updates without rescheduling), which means a nudge fires at the next pass after it becomes eligible rather than on the minute. This is the same trade the presence reminder makes — no exact-alarm permission — and it is acceptable because encouragement has no deadline. A pass that throws still returns `Result.success()`: `failure()` is a *terminal* state for periodic work, so one transient error would cancel every future pass and silence nudges until the next cold start. The daily cap is counted from the **log**, not a prefs tally, so it can't drift out of step with what was actually sent.
- **The deficit is computed but no longer shown anywhere.** `DeficitCalculator` and its tests are deliberately retained — it encodes the app's leave rule and the classification thresholds still derive from the same target — but no screen renders a deficit, and no `UiState` carries one. The redesign traded it for forward-looking encouragement; re-introducing it means adding a field back to a ViewModel, not rewriting the maths. Don't "fix" the calculator as dead code.
- **Charts are hand-rolled, and the maths is separate from the drawing.** `ui/components/charts/ChartGeometry` is pure Kotlin (no Compose, no Android) and unit-tested for the degenerate cases that would otherwise divide by zero or draw off-canvas: empty series, all-zero series, a single point, values above the ceiling. The `Canvas` composables only translate its output into draws. There is no charting dependency — adding one would be the first third-party UI library in the project. Every chart takes a `contentDescription` that states its values, because a `Canvas` is otherwise invisible to a screen reader. **`DonutChart` bounds its centred `content` itself, and that is not a convenience.** The hole is round, so its full diameter is only available along the centre line; a caption bounded by the diameter still overhangs the arc at the top and bottom of its own height. The bound is the *inscribed square* (`hole × 0.707`), applied inside the composable — the two call sites previously disagreed, with Attendance constraining to a square 72dp and Reports not constraining at all, so its caption ran out over the ring. Sizes live in `DonutChartDefaults` for the same reason: one stroke width, one diameter, both donuts. The diameter grows with `LocalDensity.fontScale` and caps, because the caption is `sp` while the ring would otherwise be fixed `dp` — past the cap the caption ellipsizes rather than being clipped mid-word.
- **Reports derives three charts from one query.** `ReportsViewModel` runs a single `dailyAggregatesFlow(trackingStart, yesterday)` and builds the daily series, the monthly series, and the all-time split from it. Both series are gap-filled: a day or month with no sessions is emitted as a real zero, since a hole in a line chart reads as missing data rather than an absence. Absent-day counts come from subtracting classified days out of the tracked window — days without sessions never reach the summary map at all.
- **The Attendance calendar is sized from the viewport.** `CalendarGrid` takes a `cellHeight` that `AttendanceScreen` derives inside a `BoxWithConstraints` from the **real** viewport — `maxHeight` less the chrome, the month selector, the weekday header and the summary card — divided by the month's actual row count (4–6, so the grid doesn't jump between months) and clamped to `48.dp..80.dp`. A cell is only ~53dp wide, so an uncapped height stretches it into a ribbon. Deriving it from `LocalConfiguration.screenHeightDp` instead is the bug this replaced: that is the whole physical screen, so it over-counted by the app bar and bottom nav and pushed the summary card off the bottom. The `48.dp` floor deliberately wins over fitting — it is the minimum tap target, so a 6-row month on a small screen scrolls slightly rather than shrinking its days below it. Selecting a day **replaces** the month-summary card rather than appending below it, so picking a date never adds height. Both averages are per *tracked* day, which keeps absent days in the denominator; the all-time one reuses the same tracking-start→yesterday range query that previously computed the deficit, so it costs nothing extra.
- **Only completed sessions aggregate** — every summary/total query filters `stopped_at IS NOT NULL`; an active session contributes nothing until check-out.
- **The presence-check reminder is configurable, and its two settings are the only thing that decides whether the clock freezes.** `presence_check_enabled` (default on) decides whether a check is armed at all — when off, `PresenceCheckRunner.arm` cancels the alarm instead of setting one, and a session runs start-to-finish unverified. Check-in and check-out stay gated regardless; only the *mid-session* re-check is optional. `presence_check_pauses` (default on) decides the consequence, and the copy is chosen to match (`reminder_text_paused` / `reminder_text_running`) — the copy must always state what ignoring it costs, because the previous single string described an etiquette request while silently stopping the user's clock. **Both settings reach the session that is already running, not only the next one** — `SettingsViewModel` writes the pref *and* calls `ServiceController.presenceSettingsChanged()` (`ACTION_PRESENCE_SETTINGS_CHANGED`), which reconciles against the DB and then `applyPresenceSettingsChange()`. That command uses `startForegroundService`, so it reaches a session whose service has been killed rather than silently doing nothing. Prefs alone were not enough, and the case that forced this is a check already outstanding: **turning the check off, or turning off its penalty, has to close the open pause**, because nothing else can — a pause closes only on a notification tap or the in-app Resume button, and with the check off neither will ever happen, so the user would lose the rest of the session's hours for a question they had just said they didn't want asked. The same handler re-arms when the check is switched *on* mid-session. Already-settled `paused_ms` is never revisited; only the open window is.
- **The presence check runs off an inexact wake-up alarm, and an unanswered one is asked again.** `PresenceCheckRunner.arm` schedules a single `AlarmManager.setAndAllowWhileIdle(RTC_WAKEUP, …)` at a random point in the `[50%, 100%]` window of the day's present mark (`ReminderScheduler`, unchanged). `PresenceAlarmReceiver` handles the fire **itself** rather than waking the service, because the alarm's whole purpose is to work when the service is gone — and starting a foreground service from a background broadcast would be refused in exactly that case. It reads the DB, posts the check, and (in pause mode) opens the pause window. **The pause is stamped when the question was actually asked, never at the scheduled instant** — an inexact alarm is allowed to land late, and back-dating would delete hours the user worked while nothing had been asked of them, on an immutable row. **Ignoring it is no longer terminal:** each unanswered check arms the next via `PresenceCheckPolicy` (30m → 60m → 2h, then holding at 2h forever), and retries post silently so they accumulate on the shade rather than buzzing all night. That is the fix for a forgotten check-out: the old single-shot flag latched on the first fire, so one missed 3am reminder meant silence for the rest of a sixteen-hour session. Re-auth (reminder tap → root `REAUTH` gate, **or** the in-app **Resume** button → `serviceController.rearm()`) folds the unverified gap into `paused_ms` and arms a fresh check. There is still no auto check-out — the row stays open; only its `duration` excludes the gap. **Why inexact:** the check fires anywhere in a multi-hour window, so exactness buys nothing, while `SCHEDULE_EXACT_ALARM` is denied by default from Android 14 and `USE_EXACT_ALARM` is restricted by Play to alarm-clock apps. **Never `setAlarmClock`** — it is the only alarm API that shows a status-bar alarm icon and a lock-screen entry.
- **An open session with no service is a real state, and three callers fix it.** `START_STICKY` is best effort — a force stop, an OEM background-management kill or a crash all leave the process dead with the row still open — and nothing used to restart the service afterwards: it was started at check-in and nowhere else. Opening the app did not help either, because the Check-In screen renders from the row, so it showed a cheerfully running timer with nothing behind it. `SessionWatchdog.reviveIfNeeded` now runs from `MainActivity.onStart`, `BootReceiver`, and the hourly `NudgeWorker` pass, in that order of reliability: **a visible Activity is always allowed to start a foreground service, `BOOT_COMPLETED` is exempt, and a worker may be refused outright.** A refusal is logged as `DEGRADED` rather than thrown, and the next caller retries — which is why there are three and not one. `ServiceController.revive` returns a `Boolean` for exactly this, and `reviveIfNeeded` catches everything: its callers are fire-and-forget `launch`es on a scope with no exception handler, so a throw would kill the process this exists to recover. **The revive is `ACTION_REVIVE`, never `ACTION_START`** — the check-in path takes its timing from the intent and zeroes `pausedMs`/`pauseStartedAt`, which is right for a session that hasn't begun and wrong for one already carrying paused time (the notification over-reports, and a frozen session shows a running clock). It also leaves the alarm alone: a killed process does not cancel alarms, so there is nothing to re-arm and arming would reset the retry escalation. A **reboot** does clear them, which is why `BootReceiver` is the one caller that arms explicitly.
- **`CheckInService.isRunning` tracks the notification, not the object.** It is set from a *successful* `startForeground` and cleared when that call throws (it is guarded — a background-start refusal or a foreground-type restriction must not kill a running session), on teardown, and in `onDestroy`. Setting it in `onCreate` instead is the bug this replaced: a caught `startForeground` failure left the instance alive with nothing on the shade, reporting itself healthy forever, and `SessionWatchdog` skipped the one state it exists to repair.
- **`serviceScope` carries a `SupervisorJob` *and* an exception handler, and it needs both.** A `CoroutineExceptionHandler` reports a failure; it does not contain one. Under a plain `Job()` the first uncaught throw in any `serviceScope.launch` cancels the scope permanently, and every later command — reconcile, re-arm, arm — becomes a silent no-op for the life of the service. That is worse than the crash it replaces: a user whose clock is frozen taps the presence notification to resume, and nothing happens, then or ever. The throw sources are real (`getActiveSession` on SQLite, the engagement-log write, `setAndAllowWhileIdle` past the 500-alarm cap). For the same reason the two `log*` helpers launch on **`applicationScope`**, not here — half of what is worth recording happens as the service ends (`STOPPED`, and the `DEGRADED` row the handler itself writes), and `onDestroy` cancels `serviceScope`.
- **Reboots need their own handler.** `START_STICKY` does not survive a restart and neither do alarms, so `BootReceiver` both revives the service and re-arms the presence check. The re-arm is anchored at **now**, not at the session's original check-in: re-deriving from the original anchor could put the instant in the past and fire the check the moment the device finishes starting up.
- **The diagnostics card ships in release, on purpose.** The event log used to sit inside the `BuildConfig.DEBUG` nudge harness, which meant that on the build people actually run there was no record of anything the notification or service layers did. Every failure down there is silent by nature — a refused post, a service killed overnight, an alarm outliving its session — so a user hitting one had nothing to report but the wrong number it left behind, and diagnosing it meant reasoning backwards from that number alone. The card is collapsed by default; the force-send harness stays debug-only.
- **Three separate switches silence a notification, and the permission is only one of them.** A user can hold `POST_NOTIFICATIONS` and still have notifications off for the whole app, or set an individual channel to "None" — which is exactly what "I had everything enabled" turns out to mean. So `AndroidNotifier.canPost` checks all three (permission, `areNotificationsEnabled()`, channel importance, plus a missing channel, since a post to one that was never created is discarded), and Settings' warning card checks the same ground: it distinguishes *everything off* from *the timer or reminder channel muted* and says so, since the copy for one is wrong for the other. The engagement channel is deliberately **not** in that check — nudges are opt-in, so muting them is a preference, not a fault. `POST_NOTIFICATIONS` is only ever *asked* for inside `PresenceGate` and Android stops showing that dialog after two refusals, so without the card an install can sit permanently with the timer, the presence check, its pause and every nudge silently dead while every screen looks normal. The card re-reads on resume, because its only escape hatch is system settings, which returns with no result.
- **Gated check-out from the notification.** The ongoing timer notification's "Check Out" action opens `MainActivity` with `EXTRA_CHECK_OUT` (not a silent `ACTION_STOP`), so it runs the root presence gate and checks out on success — check-out is **never** un-gated. `ServiceController.stop()` (`ACTION_STOP`) now only ends the service *after* a check-out has already been written.
- **Pause accounting lives on the session row, computed in two places.** The service tracks pause state in memory (mirrored to `checkin_timer_prefs`) purely to freeze its own notification elapsed; the DB row's `paused_ms`/`pause_started_at` are authoritative for the final `duration`. `beginPause`/`resumeFromPause` are read-modify-write over the active session (matching `checkOut`'s pattern). Both the service notification and the Check-In screen compute elapsed as `now - started_at - paused_ms - openPause`, which freezes while a pause is open (the open-pause term cancels the tick).
- **The Check-In screen is a fixed, non-scrolling layout — keep it that way.** The gauge and the primary button must both be reachable in one viewport and one thumb reach, so the screen is a weighted `Column`, not a `LazyColumn`, and the day's sessions collapse behind a tap. A weighted `Column` *clips* rather than scrolls when content outgrows the viewport, so `BoxWithConstraints` picks a compact scrolling branch below `560.dp` of height (landscape, very small phones, large font scales) and sizes the gauge from the available height. **A `Column` measures its non-weighted children in declaration order**, so anything declared above the button claims space before it and can coerce it to zero height — which is why the expanded session list is capped at what's left after the chrome, the gauge and the 64.dp action, and why the screen falls back to scrolling when that remainder is too small to be worth showing. Adding anything to this screen means re-checking that it still fits — and note the scrolling branch cannot host a `LazyColumn` (it would be measured with unbounded height and crash), which is why the expanded session list has two renderings.
- **The Check-In screen colours the action, never the outcome.** The primary button is a start/stop control: `startActionColors()` (green) to check in or resume, `stopActionColors()` (red) to check out, animated across the switch so it reads as one control changing state. Both come from `ui/theme/Color.kt` and deliberately reuse the calendar's present/absent hues rather than introducing a second green and red; each container/label pair clears WCAG AA. Red there is the stop half of start/stop, **not** `colorScheme.error` and not a verdict — the gauge is still brand primary until the target is met, and the `ABSENT`/`HALF DAY` badge, the target caption and the deficit row remain removed from this screen. It exists to invite the next check-in, not to grade the user. `statusColor()` supplies the same scale to the Attendance calendar, where reviewing past days is the point.
- **One 1-second ticker, on screen only.** The Check-In screen runs a composition-scoped `LaunchedEffect` that ticks the on-screen elapsed time while that screen is visible. The service has **no** ticker: its notification uses `setUsesChronometer(true)` + `setWhen(started_at + paused_ms)`, so the platform draws the running clock from a single post and keeps counting correctly through deep sleep. Both share the same origin — the DB row's `started_at`, passed to the service via `EXTRA_START_TIME` — so they agree rather than drifting by the check-in→service-start latency. **Do not reintroduce a service-side ticker.** The old one re-issued `startForeground` every second, which over a 16-hour session was ~57,000 main-thread binder calls into system_server, ~57,000 unguarded chances to throw inside a scope with no exception handler, and the behavioural signature OEM background management kills apps for — while still freezing in deep sleep, because a coroutine `delay` is scheduled on uptime and uptime stops when the CPU does. The chronometer costs one post and has none of those properties. Note the body copy must **not** also print the elapsed time while running (`notification_running`, not a formatted duration): the chronometer renders in the timestamp slot, so printing it twice shows it twice, and the printed one would be frozen.
- **Midnight attribution:** a session belongs wholly to its check-in `date_key`, even if it ends the next day (immutable single row). Asserted in `CheckInRepositoryTest`.
- **CSV export** writes to `cacheDir/exports/` and shares via `FileProvider`; it fills gap days as `FULL_DAY_LEAVE`. **Both ranges are therefore clamped to the tracked window at both ends** — that gap-filling is exactly why. "This Month" is `max(1st, tracking_start) .. min(end-of-month, yesterday)`: unclamped, the late end wrote every remaining day of the month out as a recorded absence including dates that had not happened, and the early end asserted absences for days before the user had ever opened the app — the same file the All Time export got right. "All Time" runs `tracking_start .. yesterday` for the same reason today is excluded everywhere else. **A range holding no completed day returns `ExportResult.Nothing`** (a distinct outcome, *not* a `Failure` — nothing went wrong) and writes no file. That test is on the *query result*, not just on an inverted range: a week of abandoned check-ins gives a perfectly well-formed range whose CSV would be pure gap-fill. `ReportsViewModelTest` pins each case.
- **One drawable is the launcher icon, the splash icon and the themed icon.** `drawable/ic_launcher_foreground.xml` is referenced by the adaptive icon *and* by `windowSplashScreenAnimatedIcon` in `themes.xml`, so they cannot drift. They did before: the adaptive icon pointed at `@mipmap/ic_launcher_foreground` (a raster) while the splash pointed at `@drawable/ic_launcher_foreground` (a different vector) — same name, different resource type, two different logos, and nothing flagged it. Keep both pointing at the one drawable. The old raster was also a *baked, pre-masked* icon used as a foreground layer, which hid the background entirely and got clipped by launcher masks; the layers are now genuinely separate (flat indigo background, transparent stroke-only foreground). The `<monochrome>` layer for Android 13+ themed icons points at that same foreground rather than copying its path — a second copy is precisely how the two marks drifted last time. Density-specific `mipmap-*/ic_launcher*.webp` files are **deliberately absent**: at minSdk 34 `mipmap-anydpi-v26` always wins, so they were unreachable weight.
- **The app's own code makes no network calls, and every outbound link is an implicit intent — but the merged manifest is not permission-free.** `AndroidManifest.xml` declares six permissions and networking is not among them (`RECEIVE_BOOT_COMPLETED` is now declared by the app itself, for `BootReceiver`; there is deliberately **no** exact-alarm permission — see the presence-check entry above); the **merged** release manifest, however, adds `INTERNET`, `ACCESS_NETWORK_STATE` and `WAKE_LOCK` from transitive dependencies (`INTERNET` comes from `transport-backend-cct`, pulled in by ML Kit — check `app/build/outputs/logs/manifest-merger-release-report.txt`). So the honest claim is "attendance data never leaves this device", **not** "the app holds no internet permission" — the second is checkable by any user in system settings and is false. `ui/about/ExternalLinks` is the one place app code reaches outside: the browser fetches the privacy policy, the mail app sends feedback (`ACTION_SENDTO` + `mailto:`, so it resolves to mail apps only — `ACTION_SEND` would offer every share target), and the Play app handles the rating. Adding a network call anywhere means a new Data Safety declaration — the reason the feedback path is an email the user reads and edits before sending, not a silent POST. Each launcher returns `false` instead of throwing so callers fall back to the clipboard; both `ActivityNotFoundException` (no browser, no mail app) and `SecurityException` (a handler in another profile) are real outcomes, so both are caught.
- **The open-source licence list is hand-maintained, and it is grouped on purpose.** The release runtime classpath resolves to ~220 artifacts that collapse into the upstream projects in `ui/about/OpenSourceLibraries`. **The list is the classpath, not the dependency block** — regenerate it with `./gradlew :app:dependencies --configuration releaseRuntimeClasspath` and group by Maven group id. Listing only the direct dependencies is the bug this replaced: it omitted seven projects, all of them redistributed in the APK, most of them dragged in under ML Kit (`com.google.android.gms`, `com.google.android.odml`, `com.google.android.datatransport`, `com.google.firebase`, plus `org.jetbrains:annotations`, `org.jspecify`, `javax.inject`). Grouping is only sound because the licence is uniform *within* a group, which is why three groups carry non-Apache terms: **ML Kit face detection is not Apache-2.0** (its POM declares "ML Kit Terms of Service"), **`com.google.android.gms` and `com.google.android.odml` declare the Android Software Development Kit License**, and `androidx.camera:camera-core` declares BSD alongside Apache-2.0 for the libyuv it embeds. Don't fold any of them back into an Apache row. `OpenSourceLibrariesTest` guards the list's shape and asserts those non-Apache groups stay non-Apache, but it cannot see the Gradle graph — that half is **`./gradlew :app:verifyLicenseCoverage`**, which resolves `releaseRuntimeClasspath` and fails naming any group id no entry's `coordinates` covers. It also checks `res/font/`, because a typeface is redistributed exactly like a dependency but has no Maven coordinate — those entries carry `coordinates = "font:<resource name>"` (with a `font:family_*` wildcard covering a family's weight cuts) and are matched against `res/font/` instead, or a font dropped in would ship unattributed and pass silently. Only files aapt would package as a font count (`.ttf/.otf/.ttc/.xml`) — an unfiltered listing fails the build naming a `.DS_Store` a Finder visit left behind. It runs in CI (with the tests, not with `staticAnalysis`, which is kept free of dependency resolution) and hangs off `check`, and it declares an output stamp so it is UP-TO-DATE when neither the list nor `res/font/` changed: a task with inputs but no outputs can never be skipped, and this one resolves the whole release classpath. It parses the `coordinates = "…"` lines out of the source file, so it fails loudly if that format ever changes rather than passing on an empty parse. What it deliberately does **not** do is generate the list: a POM-reading generator produces ~220 flat rows and loses both the grouping and the hand-written notes, so drift detection is automated and the wording stays human. Licence text ships in `res/raw` rather than being linked wherever the terms oblige a copy — `apache_2_0.txt` for the code, `ofl_1_1.txt` for the typefaces — because an offline device could not otherwise read it. Which licences get that treatment is `LibraryLicense.bundled`, and the Licenses screen **loops over that flag** rather than hardcoding a block per licence; the raw-resource mapping lives in `LicensesScreen` so the enum stays plain Kotlin the unit tests can read. Each toggle names its licence, since these buttons sit below every card with no other context, and the paragraphs stay individual `items` of the `LazyColumn` — a single `Text` holding 11 KB measures all of it on the frame it appears, which is long enough to see.
- **One description of a notification, one place that builds it, one place that posts it.** All three — the ongoing timer, the presence check and every nudge — are declared as a `NotificationSpec` and built by `NotificationFactory`; `Notifier.show()` then adds the `POST_NOTIFICATIONS` guard and posts. Building and posting are **separate** because `startForeground` needs the `Notification` object in hand and must succeed with or without the permission, so the timer goes `factory.build(...)` → `startForeground` while everything else goes through the guarded `notifier.show(...)`. **That applies to the per-second update too, not just the first post** — re-issuing `startForeground` updates the notification in place and is exempt from the permission, whereas routing the tick through `notifier.show` freezes the displayed elapsed time the moment `POST_NOTIFICATIONS` is revoked while the notification itself stays on the shade. Hand-building a notification anywhere else re-opens the bug this closed: the presence check used to bypass the guard, so a revoked permission meant a `SHOWN` logged for a notification nobody saw *and* a clock frozen over a question never asked. Ids live in `NotificationIds` (service) and on `Nudge.notificationId` (one per nudge, **never reused** — a shared id makes a second nudge silently replace the first, and an ordinal-derived one reshuffles when the enum's priority order changes). `NotificationIds.RETIRED_SHARED_NUDGE` is the one id nothing posts under: it is what every nudge shared before, and `EngagementReporter` still cancels it so a nudge posted by the *previous release* can be retired after an update. **`PendingIntent` request codes are a namespace shared with previously installed versions**, and equality ignores extras, so `NotificationFactory` offsets them (`CONTENT_REQUEST_BASE`/`ACTION_REQUEST_BASE`) rather than using the bare notification id — the old build's presence-check content intent was request code 1, which is now the timer's id, and `FLAG_UPDATE_CURRENT` would rewrite a still-posted notification's tap target across the update.
- **A refused post no longer writes the check off.** When `notifier.show` is false — in practice `POST_NOTIFICATIONS` revoked — `PresenceCheckRunner` logs a `DEGRADED` row, opens no pause (the user was never asked, so nothing may be charged for), and **re-arms anyway without consuming an attempt**. Restoring the permission therefore resumes the checks. The behaviour this replaced marked the check spent on a refusal and never asked again for the rest of the session, so a revoked permission silently disabled the whole mechanism until the next check-in. Silence is not an answer, which is why a refused post must not advance the retry escalation. Refusals do carry a back-off **of their own** (`PresenceSchedule.refusals`, the same 30m/60m/2h ladder, cleared by the first post that succeeds): sharing the attempt counter would consume the escalation, but re-asking every thirty minutes until check-out wakes the device all night on behalf of a message that cannot appear.
- **Nothing is `autoCancel`, and that is what makes a dismissal mean something.** The platform can deliver a delete intent when an auto-cancel *tap* removes a notification, which is indistinguishable from a swipe — so `NotificationFactory` always sets `setAutoCancel(false)` and whoever handles the tap cancels explicitly (`EngagementReporter.onNudgeOpened` for nudges, `rearmReminder()` for the presence check). An app-initiated `cancel()` delivers no delete intent, so everything reaching `NotificationDismissReceiver` is a genuine dismissal, recorded as `DISMISSED` via the pure `DismissRouting.resolve`. **The presence check is deliberately cancelled only on a successful re-arm, not on the tap** — under `autoCancel` a tap that abandoned the gate removed the reminder while leaving the clock paused, stranding the user with a frozen timer and nothing to tap.
- **Only a notification tap counts as an acknowledgement.** `ServiceController.rearm(fromNotification)` is true from the `REAUTH` gate and false from the in-app Resume button; both resume the clock identically, and the flag decides only whether `OPENED` is logged. Wiring it to every re-arm reported an open rate for a message the user may never have seen.
- **Notification icons are the brand mark, not platform stock.** `ic_stat_checkin` (a 24dp silhouette from the same geometry) is the small icon for the timer, the reminder and every nudge; `ic_stat_check_out` matches `Icons.AutoMirrored.Filled.Logout`, which the UI already uses for that action. Status-bar icons keep only their alpha channel, so they must stay white-on-transparent.

## Conventions

- Kotlin official code style; Composables PascalCase. `./gradlew ktlintFormat` is the arbiter — don't hand-format against it.
- **Time arithmetic goes through named unit constants, never inline `60 * 60 * 1000`.** `util/TimeFormat` declares the millis/seconds/minutes/hours ladder for formatting; `TargetSchedule` and `DefaultCsvExporter` carry their own `MILLIS_PER_HOUR` because they convert rather than format. Detekt's `MagicNumber` enforces this outside Composables, where dp/sp/alpha literals are exempt.
- Each screen observes **one** `uiState: StateFlow<XUiState>` via `collectAsStateWithLifecycle`; VMs are constructor-injected from `AppContainer` through a `viewModelFactory`. Add a `LifecycleResumeEffect { onResumed() }` so prefs/target changes re-read on return to a screen; the day-rollover is handled reactively by `TimeSource.currentDay()`, not gated on the resume.
- All DAO/repository DB operations are `suspend` (or return `Flow`); Room via **KSP**.
- Status colors come from `ui/theme/statusColor(...)` (light/dark tuned) — never hardcode them in screens.
- **Dates the user reads are formatted in `util/TimeFormat` and nowhere else.** `dateWithYear` ("Jul 25, 2026") for a date read in isolation; `dateWithWeekday` ("Saturday, Jul 25") where the surroundings already supply the year and the weekday earns the space instead; `dateKeyWithWeekday` for the nullable ISO `date_key` the screens hold, returning null rather than throwing on a malformed one. Both patterns are the same abbreviated-month family, so a date is recognisably a date wherever it appears. Scattering them across call sites is the bug this replaced: Reports printed a raw `LocalDate.toString()` ("2026-07-25") and Attendance printed a raw `date_key` under "Sessions on". **`date_key` itself stays ISO** — `CheckInSessionDao` range queries depend on its lexicographic ordering, and the CSV `Date` column is machine-read; only the display side goes through `TimeFormat`.
- Duration/clock formatting goes through `util/TimeFormat` — do not re-implement it. `durationLive` ("0m 0s" → "59m 59s" → "1h 0m") is for a *ticking* clock only — the Check-In gauge and the open interval; everything settled (totals, reports, CSV, past sessions) uses `durationShort`, where seconds would be noise.
- **Two bundled typefaces, split by reading size** (`ui/theme/Type.kt`): **Outfit** on display/headline/title, **Manrope** on body/label. The split follows from their x-heights (0.460 em vs 0.540) — Outfit reads as elegant on the 45sp gauge and thin in a 12sp row, Manrope the reverse; swapping them is the mistake the arrangement exists to prevent. Each weight is a **static instance cut from the upstream variable font**, four per family. The variable files would be 331 KB smaller, but selecting a weight out of one needs `FontVariation.Settings`, which is `@ExperimentalTextApi` — and without pinning the axis the file loads at its default instance and the platform fakes the heavier weights by smearing glyphs. Real cuts buy a stable API and genuine weights; **don't "optimise" this back to two variable files without reintroducing that opt-in.** Only `fontFamily` is overridden — every M3 size, line height and letter spacing is untouched. **`TextStyle.tabularFigures()` on the ticking clock is load-bearing, not polish:** Outfit's default `1` is 321 units against `0` at 659, a 2.05x spread that makes the gauge lurch sideways once a second without `tnum`. Both families resolve the feature to uniform widths (Outfit 590, Manrope 1240), and instancing preserves it along with the embedded copyright notice — check both if the cuts are ever regenerated. Bundling costs 608 KB of resources and means the app no longer honours a device font *choice* — font *scale* is still honoured, everything stays in `sp`.
- **String casing follows the header comment in `strings.xml`.** Section and card titles are Title Case ("Daily Target", "Overall Stats"); everything read as a line rather than a heading — row labels, buttons, help text, empty states — is sentence case ("Mid-session presence check", "Grant access"). The exceptions are the product name CheckIn, the "Check In"/"Check Out" actions it is named after, and the PRESENT/HALF DAY/ABSENT badges, which are styled as badges rather than read as words. The Reports stat rows are the drift this rule was written from: they were Title Case with a sentence-case parenthetical bolted on ("Current Streak (target met)") while every Settings and About row beside them was sentence case.
- Material 3 with a **fixed brand color scheme** (indigo seed, `ui/theme/Theme.kt`) — dynamic color is intentionally not used — plus system dark mode and a branded splash. Large screens are width-capped (`ui/components/ConstrainedContent`) and Attendance goes two-pane on expanded widths (`WindowSizeClass`).
- **The brand mark is generated, not drawn.** `play-store-assets/generate_icons.py` owns the geometry and emits the `pathData` for `drawable/ic_launcher_foreground.xml` and `ic_stat_checkin.xml`, plus the 512px Play icon — change it there and paste the printed paths back, never hand-edit a path. Its `verify()` asserts the adaptive-icon safe circle on every run.
